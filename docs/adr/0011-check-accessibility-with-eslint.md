# JSX のアクセシビリティは ESLint で確かめる

mojisashi は、キーボードだけで使う人や、スクリーンリーダーで使う人にも使えるページにします。ただ、ラベルのない入力欄や、クリックでしか動かない `div` は、型のチェックでもテストでも止まりません。エージェントが書いたコードに入っても、気づけないまま公開されます。

そこで、ADR 0003 のとおり、機械的に止めます。ESLint で eslint-plugin-jsx-a11y-x の `strict` を、すべての `.tsx` に使います。`src/app/`、`src/platform/`、`src/shell/` と `guard-probes/` が入ります。`bun run lint` は警告が1つでもあれば失敗するので、ルールに引っかかったコードはコミットも PR のマージもできません。

`strict` を選んだのは、`recommended` が例外を認めているためです。たとえば `recommended` は、`ul` や `fieldset` のような操作するためではない要素に、`listbox` や `radiogroup` のような操作するための役割（role）を付けても止めません。役割を付けても、キーボードで操作できるようにするコードは別に要ります。`strict` は、こうした例外を認めません。

元の eslint-plugin-jsx-a11y ではなく、jsx-a11y-x を使うのは、次の理由です。

- 元のプラグインは、最後の版が 6.10.2（2024年10月）です。対応する ESLint は 9 までで、mojisashi が使う ESLint 10 には対応していません。
- jsx-a11y-x は元のプラグインから分かれたもので、ルールは同じです。ESLint 9 と 10 に対応し、ESM で書かれています。直接依存するパッケージは、元の15個に対して7個です。

ルールの名前は、`jsx-a11y/` ではなく `jsx-a11y-x/` で始まります。ルールが働くことは、`guard-probes/` の `blocked/` に置いた probe で確かめます。

ESLint はコードしか見ないので、次のものは確かめられません。

- 文字と背景の色の差（コントラスト）
- キーボードで移る順番と、フォーカスの見え方
- スクリーンリーダーが読み上げる順番と内容

これらは、本番に出す前に、ブラウザで開いたページで確かめます（issue #14）。

## Considered Options

- **元の eslint-plugin-jsx-a11y を使う。** 使う人が多く、よく知られたプラグインです。ただ、ESLint 10 に対応した版がなく、入れるには依存の食い違いを無視することになります。
- **`strict` ではなく `recommended` を使う。** 引っかかるコードは減ります。ただ、例外を認めた分だけ、エージェントが例外に頼って書いたコードを止められません。決まりは機械的に止めるという ADR 0003 に合わないので、`strict` にしました。
