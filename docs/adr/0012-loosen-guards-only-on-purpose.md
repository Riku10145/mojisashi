# 守りは、チェックを通すためにはゆるめない

ADR 0007 は、守りを決めるファイルが変わった PR を CI の「Guards」で失敗させ、人が中身を確かめてからマージすると決めました。これをやめます。

やめる理由は2つです。

- Guards は、入れたあとの PR 4件（#5、#7、#8、#19）のすべてで失敗しました。守りを足す変更も、ゆるめる変更と同じように失敗するためです。毎回失敗するチェックは何も知らせません。失敗したままマージするのに慣れると、ほかのチェックの失敗も見落としやすくなります。
- mojisashi では、人が PR のコードを読みません。Guards が出すのは変わったファイルの名前で、ゆるめたのか足したのかは、差分を読まないと分かりません。確かめる人がいないので、知らせても使われません。

守りは、いずれゆるめることがあります。いまの一覧はきびしく、機能を足すと、新しい要素やブラウザの仕組みが要るようになるためです。エージェントが、機能に要ると決めてゆるめるのはかまいません。してほしくないのは、チェックに止められたときに、コードを直さず、通すためだけに一覧へ足すことです。

この2つは、差分ではどちらも「一覧に1行足した」に見えます。違うのは理由なので、CI は変更の中身から見分けられません。そこで、エージェントがゆるめるかどうかを決める場面で読むものに、この決まりを書きます。

- **ESLint のエラーの文言。** 一覧にないものを使って止まったとき、文言は「コードを直してください。このエラーを消すために `guards/zones.ts` へ足すことはしません。機能に要ると決めたときだけ足します」と伝えます。前の文言は「`guards/zones.ts` を見てください」で、足せば通ると読めました。
- **`CLAUDE.md`。** 「人に確かめてもらいます」をやめ、同じ決まりを書きます。

`.github/workflows/guards.yml`、`.github/guards-unchanged.sh`、`.github/guarded-paths` は削除します。ADR 0007 のほかの決まりは変えません。PR の中のチェック（`bun run check`）は、これまでどおり CSP、`minimumReleaseAge`、コマンド、ファイルの種類を確かめます。

この決まりは文章で頼むもので、破っても機械的には止まりません。ADR 0003 は、決まりを機械的に止められる道具で守ると決めていますが、理由を見分けられる道具がないためです。ADR を書き換えないことも、Guards がなくなるので、`CLAUDE.md` の決まりだけで守ります。

## Considered Options

- **Guards を残し、失敗ではなくコメントやラベルで知らせる。** CI は本当に失敗したときだけ赤くなります。ただ、知らせを読んで差分を確かめる人がいないので、知らせる先がありません。
- **対象のファイルを減らす。** 失敗した4件のうち3件は `guards/` を、残る1件は `eslint.config.ts` を変えていました。守りの中心のファイルなので、対象から外せず、減らしても毎回失敗します。
- **一覧が増えた PR に、理由を書いた ADR の追加を求める。** 1行足して済ませる前に、理由を文章にする手間が入ります。ただ、要素を1つ足すたびに ADR が要ることになり、機能を作る普通の作業まで遅くなります。通すためにゆるめる変更が実際に出たら、あらためて考えます。
